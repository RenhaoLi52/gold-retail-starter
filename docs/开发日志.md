1. *Command Line Tools 安装失败（invalid developer directory）*——机器上有完整版 Xcode，独立 CLT 根本不用装，`sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer` 把指针指回 Xcode 即可。教训：报错先读字面意思，"目录无效"就是指针指错了。

## 2026-10-01 · 第 2 章：接入 PostgreSQL（v0.2）

**做了什么**：`database/sql + lib/pq` 连接 Docker 里的 PG16；入库改为一个数据库事务；发号器落到 `doc_counter` 表；每件货写 `stock_flow` 库存流水。

**关键决策**：
- 驱动选 `lib/pq`（零依赖、database/sql 标准接口）而不是 pgx——对入门更友好，将来要换也只是换 import。
- "全有或全无"从"代码小心点"升级为**数据库事务保证**：`db.Begin()` → 全部成功 `Commit()` / 任何失败 `defer Rollback()`。
- 发号器 SQL：`INSERT ... ON CONFLICT ... DO UPDATE SET seq=seq+1 RETURNING seq`——一条语句完成取号，天然并发安全（先在 psql 里手跑两次看到 1、2，再写进代码）。
- 金额克重全用 NUMERIC；表名用 app_user（user 是 PG 保留字）；条码规则在数据库层再加 CHECK 约束兜底。

**验收仪式**：开两张单 → 重启后端 → 数据还在。`stock_flow` 里能看到每件货的"(入库)→在库"记录。

**踩坑记录**：
4. *psql 里粘贴多行 SQL 后界面卡死、报 sh 语法错误*——`\d` 的长输出进了翻页器(less)，粘贴的内容被当成按键命令。按 `q` 退出；`\pset pager off` 关掉翻页；**长 SQL 压成一行再粘贴**。

## 2026-10-01 · 第 3 章：单据状态机（v0.3）

**做了什么**：入库从"一步到位"拆成 **保存草稿 → 确认 → 反确认 / 删除草稿**。草稿明细存 `doc.draft_lines`(JSONB)，确认那一刻才生成货品件；前端加单据列表、状态徽章和操作按钮。

**关键决策**：
- **确认 = 业务生效点**：库存只在确认时变动，和单据状态变更在同一事务里（设计文档 4.2 节的落地）。
- **条件更新裁决并发**：`UPDATE doc SET status='已确认' WHERE id=$1 AND status='草稿'`——两台电脑同时点确认，数据库保证只有一台影响行数=1，另一台得到人话报错。整个系统的并发安全就建立在这一个模式上。
- **反确认的下游校验**：本单所有件必须仍"在库"，否则拒绝并指明条码（现在只有入库单，将来销售/分销单引用了件，这道闸自然生效）。
- **条码不重发**：确认时把发出的条码回写进草稿明细；反确认→再确认，条码原样复用。吊牌已经打了，条码换了就全乱了——业务常识决定技术设计。
- 草稿即占号，删除不回收（号段留空洞没问题，号被复用才是审计灾难）。

**踩坑记录**：
6. *点反确认后整个页面按钮全部失灵*——**本项目第一个真实 bug**，值得详记：
   - 现象：反确认成功，但之后点任何按钮都没反应。
   - 本质：一张单据的 items 字段返回了 null，模板里 `d.items.length` 抛 TypeError，**Vue 渲染函数一旦抛异常，整个组件树冻结**，表现为"所有按钮失灵"。
   - 排查法：界面全体失灵 ≈ 渲染异常 → 开浏览器开发者工具(Cmd+Option+I)看 Console 红字，一眼定位到行。
   - 修复（两层）：后端——反确认时从真实货品件**重建**草稿明细，且列表接口永远返回数组不返回 null（API 卫生）；前端——`d.items?.length ?? 0`、`(it.weightG ?? 0).toFixed(2)` 渲染防护。
   - 教训：后端给的数据永远可能有缺口，前端渲染永远要防 null；临时恢复手段是刷新页面，根治靠两端兜底。
7. 开发期数据可以随时清零重来：`TRUNCATE ... RESTART IDENTITY` 只清数据不动表结构。但**健壮性修复不等于兼容补丁**，该留的防护要留下。

## 附：如何用 git 倒推学习

每条提交都是整个项目在那一刻的**完整快照**，所以答案是：可以，而且不用"下载"，仓库里全都有。

常用回放命令：

```bash
git log --oneline            # 列出全部提交（哈希+说明），就是本日志的目录
git show <哈希> --stat       # 看某次提交改了哪些文件
git show <哈希>              # 看该次提交的完整代码差异（+是新增，-是删除）
git diff <旧哈希> <新哈希>   # 对比任意两个版本
git checkout <哈希>          # 把整个工作区切回那个时刻（时光机）
git checkout main            # 回到最新（看完记得回来！）
```

两个习惯让回放更有价值：**一次提交只做一件事**，提交说明写清楚"做了什么"（本仓库一直如此）；GitHub 网页上的 Commits 页签也能点开每次提交在线看差异，适合不想碰命令行的时候。

学习路线建议：`git log --oneline` 从最早的提交开始，对照本日志的章节，`git show` 逐个看差异——你会看到系统像搭积木一样从 200 行长到现在，每一步的"为什么"都在上面的章节里。

## 2026-10-01 · 第 4 章：真实账号体系（v0.4）

**做了什么**：登录改为查 `app_user` 表；密码用 PBKDF2-HMAC-SHA256 加盐哈希存储（Go 标准库 crypto/pbkdf2）；登录成功签发 JWT(HS256, 12小时过期)；鉴权中间件验证令牌并把用户id放进请求上下文；单据制单人、库存流水操作人全部换成真实 uid；新增修改密码接口和界面；首次启动若无用户自动创建 admin/123456 并提示改密。

**关键决策**：
- **数据库永远只存哈希不存明文**：`pbkdf2:迭代次数:盐:哈希` 一串存下自描述参数，将来升级迭代次数也能平滑过渡；校验用恒定时间比较防时序侧信道。
- **JWT 无状态认证**：服务端不存会话，令牌自带身份和过期时间，天然适配多终端同时登录；密钥走环境变量 `JWT_SECRET`（上线前必须换掉默认值）。
- 登录失败只回一句"账号或密码错误"——不泄露"账号是否存在"。
- 改密码必须先验旧密码；新密码至少6位（权限框架做好后可加策略）。

**踩坑记录**：
8. *首次启动 panic: value too long for type character varying(100)*——哈希串112字符超过 password 列宽。测试环境先于用户炸出，加迁移 003 放宽到 VARCHAR(200)。教训：**改了数据的"形状"（更长/更多/类型变了），先想想列宽和约束**；也再次验证"先在测试环境全链路跑一遍再交付"的流程价值。

## 2026-10-01 · 第 5 章：用户管理（v0.5）

**做了什么**：管理员可以新建店员账号、启用/禁用、重置密码；界面上管理员多一个"用户管理"面板，店员看不到。给 app_user 加 is_admin 标记（迁移004），登录返回 isAdmin，JWT 中间件每个请求实时查账号状态。

**关键决策**：
- **禁用立即生效**：鉴权中间件每个请求都查一次账号状态，而不是只信令牌——被禁用的店员即使令牌还有11个小时才过期，下一次点击就被踢出。代价是每请求多一次主键查询，这个规模完全无感；换来的是"辞退店员即刻失效"这种业务上必须的确定性。
- **不能禁用自己**：防止管理员把自己锁在门外。
- **前端隐藏≠安全**：店员界面上看不到用户管理按钮只是体验，真正的防线在服务端 requireAdmin（403）——所有权限都必须服务端裁决，前端只负责"少给人看不该点的按钮"。
- is_admin 是权限框架的临时形态：将来角色+权限点框架落地后，它会被 role 关联取代，但"服务端裁决+前端隐藏"的二层结构不变。

**验收剧本**：admin 建 wang/666666 → wang 登录（无用户管理按钮）→ wang 开单（单据 maker_id=2，制单人追溯生效）→ wang 调用户接口 403 → admin 禁用 wang → wang 旧令牌立即 401 → admin 重置密码并启用 → wang 新密码登录成功。

## 2026-10-01 · 第 6 章：基础资料字典（v0.6）

**做了什么**：首饰大类、成色、首饰类别三个字典上线——共用一张 dict_item 表、一套接口、一个三页签管理面板（仅管理员）。开单表单的大类和成色从手输/写死改为字典下拉；大类还带出销售模式（变金价/标签价，为后续计价引擎铺路）。保存单据时服务端校验大类必须是启用的字典项。

**关键决策**：
- **三个字典一张表**（dict_type 区分）：同一套增/查/停用接口服务所有字典，将来加"品牌""工艺"等新字典=插几行数据，零新代码——这是"单据引擎"复用思想在最小场景的预演。
- **字典只停用不删除、暂不改名**：历史单据和货品以名字引用字典项，删除或改名会让历史数据失去解释。停用的项不再出现在开单下拉里，但旧数据照常显示。
- **服务端校验闭环**：前端下拉只是引导，保存时服务端再验"大类存在且启用"——继续贯彻"前端是体验、服务端是防线"。
- 种子数据随迁移脚本进库（ON CONFLICT DO NOTHING 保证可重复执行）。

**验收剧本**：管理员在基础资料里新增"彩宝类(标签价)" → 开单下拉立刻出现；停用"玉器类" → 下拉消失，且后端拒绝用它开单；店员读字典正常（开单要用）、增改被 403。

### 第 6 章补记：撤销"大类绑定销售模式"（设计修订）

上线当天即被业务纠正：同一大类下既有标签价也有变金价的货品，销售模式不能挂在大类上。修订为：**入库录克重和售价，销售开单时逐件选择结算方式**（标签价→读售价；变金价→克重×当日金价/银价）。迁移 006 删除 price_mode 列，前后端同步撤除。售价字段与销售单计价引擎留待后续章节实现。

**教训（很值钱）**：参照系统（JMP）的做法不等于自己的业务事实，每个设计都要过一遍"我店里真实情况是这样吗"；以及——迁移脚本让撤销一个字段和添加一样轻量，schema 版本化的价值在第一次"改主意"时就回本了。

## 2026-10-01 · 第 7 章：首饰退库单（v0.7）—— 第一次照 checklist 加新模块

**做了什么**：退库单（TK）全生命周期上线：扫码/输入条码选总库在库件 → 草稿 → 确认（件变"已退库"）→ 反确认（件回"在库"）。对照开发计划第 8 节的 8 步 checklist 走完全程：①登记类型(TK前缀) ②明细定义(条码选件+快照) ③确认动作(条件更新 在库→已退库) ④反确认逆操作+校验 ⑤打印(待Electron阶段) ⑥权限(登录即可，暂无专项点) ⑦报表(列表即简版) ⑧回归(含并发双确认)。

**本章最重要的时刻——跨单据状态机第一次咬合**：GD777 退库后，去反确认它的入库单，被精确拒绝："条码 GD777 当前状态为「已退库」，已被下游业务占用"。反确认退库单后，入库单又能反确认了。设计文档 4.2 的"下游依赖校验"从纸面变成了真实约束——以后每加一种单据（分销、销售），这张网会自动变密，不需要改入库单一行代码，因为校验看的是**件的状态**而不是单据的种类。

**关键决策**：
- 选件校验两道闸：保存草稿时校验"存在且在库"（即时反馈），确认时再用条件更新 `WHERE status='在库'` 终审——草稿放了一夜、件被别的单占了，确认时照样拦住。
- 草稿阶段不锁定货品（锁定机制留给销售挂单一起做），靠确认时的条件更新兜底——这是设计文档 6.6"第一期关键时刻实时校验"路线的落实。
- 前端扫码框：本地先查已加载的库存给即时反馈（扫码枪即键盘，回车即添加），服务端校验仍是最终裁决。

**踩坑记录**：
9. *测试脚本"全错"虚惊*——第一轮退库测试九连败，看起来像代码全坏了，实际是前提错了：此前几轮测试留下的都是草稿单，库里根本没有在库的件。教训：**测试失败先怀疑测试场景，再怀疑代码**；每个测试用例要自带前置数据准备（先入库并确认，再测退库）。

## 2026-10-01 · 第 8 章：库存查询升级（v0.8）

**做了什么**：库存接口支持 状态/大类/关键字 组合筛选（关键字=条码前缀 LIKE 或名称模糊 ILIKE），并返回与筛选条件一致的汇总（件数+合计克重）；前端库存卡片加筛选栏、合计行、大类列，超过500条提示缩小范围。

**关键决策**：
- **汇总与明细共用同一组 WHERE 条件**——"合计"永远等于你看到的列表口径，报表最忌讳的就是合计和明细对不上。
- 动态拼 WHERE 但**参数全部走占位符**（$1,$2...），拼接的只有条件骨架——SQL 注入的门从一开始就焊死。
- 条码用前缀匹配（LIKE 'GD%'，能吃索引），名称用模糊匹配（ILIKE '%手镯%'）——两种字段两种策略，货量大了前者依然快。
- 明细限500条但汇总是全量——界面不卡，数字不缺。

这是报表引擎的雏形：以后的"入库明细表""销售统计表"都是同一个套路——一组筛选条件，一份与之口径一致的明细+汇总。

## 2026-10-01 · 第 9 章：入库加售价字段（v0.9）

**做了什么**：货品增加 price（售价/标签价，NUMERIC(12,2)，迁移007）。入库明细可录售价（按克货可填0=未定价）；售价随货品全程流转：确认写入、反确认→再确认保留、入库/退库列表与库存查询全部展示。负数被校验拒绝。

## 2026-10-01 · 第 10 章：金价发布（v0.10）

**做了什么**：gold_price 表（迁移008）+ 发布/当前价/历史三个接口 + 页面顶部"今日金价"卡片（所有人可见实时价；管理员可按成色发布零售价/回收价；调价历史可展开）。

**关键决策**：
- **价格只追加、永不修改**（append-only）：每次发布插一条新记录，"当前价"=每成色最新一条（DISTINCT ON + id DESC），一天调价多次历史全在。将来销售确认时把成交时刻的价格快照进单据——历史单据金额永远可复算，这是审计口径的根。
- 发布校验三道：成色必须是启用的字典项；零售价>0；**回收价不得高于零售价**（挡住手滑输反的经典事故）。
- 当前价接口对所有登录用户开放（店员开单要看），发布仅管理员。

至此销售计价的数据来源集齐：标签价(item.price) + 金价(gold_price) + 克重(item.weight_g)。下一站：销售单。

## 2026-10-01 · 第 11 章：销售单第一轮（v0.11）—— 系统的心脏开始跳动

**做了什么**：销售单（XS）核心闭环：扫码加货（仅在库件）→ 逐件选结算方式（标签价=读货品售价，须>0；变金价=克重×该成色今日零售金价，须已发布）→ 参考价自动算、实售价可议价修改 → 挂单(草稿)/确认收款 → 件变"已售"、金价快照+每行成交参数存档进单据、算合计 → 反确认**仅限当日**（跨日走销退，待做）。迁移009给单据头加 total_amount 与 gold_price_snapshot。

**关键决策**：
- **金价快照在"确认收款"那一刻采集**（事务内查最新发布价），不是加入购物车时——草稿挂了一小时、金价变了，以确认时为准；快照里每行存 mode/goldRate/refPrice/soldPrice/labelPrice，议价留痕（参考价 vs 实售价的差一目了然，将来折扣权限阈值就卡在这）。

- 并发裁决依旧一个模式：确认时逐件 `UPDATE ... WHERE status='在库'`，两个柜台抢同一件，后到者收到"可能刚被其他柜台售出"。
- 加货默认结算方式智能选择：有标签价默认标签价，否则变金价；无标签价的件禁选标签价。

**验收剧本（已全部通过）**：未定标签价选标签价被拒；未发布金价成色选变金价被拒；金链变金价(12.5g×812=10150)+玉镯标签价4980议到4900 → 确认合计15050 → 快照落库 → 已售件退库/再销售均被拒 → 当日反确认库存恢复 → 伪造跨日单反确认被拒。

## 2026-10-01 · 第 12 章：套上 Electron 壳（v0.12）—— 从"网页"变成"应用"

**做了什么**：给前端套上 Electron 桌面壳。新增 `client/electron/main.cjs`（主进程：开一个 1280×860 的窗口，标题"黄金零售系统"，中文菜单）；`package.json` 加 `main` 入口、`electron` 启动脚本和 electron 依赖；`vite.config.ts` 加 `base: './'`；`api.ts` 加 API_BASE 判断。界面代码一行没动。

**怎么理解 Electron**：Electron = 一个内置了 Chrome 内核和 Node.js 的"浏览器外壳"。我们的 Vue 界面原本跑在浏览器标签页里，现在改由这个壳加载——同一份前端代码，两种出口。VSCode、钉钉、微信小程序开发工具都是这么做的。这正是当初选型的理由：**一套代码，Mac 和 Windows 都出桌面应用**。

**关键决策**：
- **主进程刻意保持最小**（40行）：只负责开窗口+菜单。业务逻辑一点不往主进程放——主进程越薄，Mac/Windows 差异面越小。
- **开发/打包两种加载方式**：开发时环境变量 `VITE_DEV_SERVER_URL` 存在 → 加载 Vite 开发服务器（热更新照常）；打包后加载构建出的本地文件 `dist/index.html`。
- **`contextIsolation: true`**：渲染页面与 Node 隔离，Electron 的安全默认。我们的界面只跟 Go 后端 API 说话，不需要碰 Node 能力（将来打印需要时再通过 preload 白名单开小口）。
- **api.ts 的 API_BASE**：开发模式页面是 http:// 走 Vite 代理不变；打包后页面是 file://，没有代理，自动改为直连 `http://localhost:8080`。一个三元表达式兼容两种模式。
- **`base: './'`**：Vite 构建默认用绝对路径 `/assets/...`，file:// 下会找不到文件，改相对路径 `./assets/...` 才能在壳里加载。

**先欠着的账（打包章再还）**：打包成 .dmg/.exe（electron-builder）、file:// 直连后端时的 CORS 放行、Go 后端随应用启动、打印功能。现在先用"三终端开发模式"看效果。

**踩坑预告（中国网络）**：`npm install` 下载 Electron 二进制默认走国外服务器，大概率超时。安装前先 `export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 换国内镜像——这与 Homebrew/go proxy 换源是同一个道理。

## 2026-10-01 · 第 13 章：登录态持久化（v0.13）—— 刷新不再"被登出"

**问题由来**（用户发现）：JWT 有效期明明是12小时，为什么一刷新页面就要重新登录？答案：服务端从没登出过你——令牌存在 `api.ts` 的一个内存变量里（`let token = ''`），刷新页面 = JS 世界推倒重来，变量清零，钥匙丢了。**令牌的"有效"和客户端"还记得它"是两回事。**

**做了什么**：
- `api.ts`：令牌同步存入 `localStorage`（浏览器/Electron 自带的本地小仓库，刷新/重开窗口不丢）；启动时先从仓库恢复；收到 401 时顺手清掉废令牌。
- 后端新增 `GET /api/me`：拿旧令牌问"我是谁"，返回 username/name/isAdmin。
- `App.vue`：`onMounted` 时若有保存的令牌就调 `/api/me`，成功则直接进系统；失败安静地留在登录页。顺带补了"退出登录"按钮（以前刷新就是登出，现在登录会一直保持，必须给个正经出口）。

**关键决策**：
- **恢复登录态必须过一遍服务端**（/api/me），不能只看本地有没有令牌就放行——withAuth 里会实时查账号状态，被禁用的人即使令牌没过期也会被 401 弹回登录页。本地仓库只存令牌这一样东西，用户名/是否管理员每次都以服务端的回答为准（管理员权限被撤了，重启应用立刻生效）。
- 401 时自动清除本地令牌：废令牌留着只会让下次启动多一次注定失败的请求。
- `localStorage` 读写都包了 try/catch：个别受限环境没有它，退化成老的纯内存模式，不至于白屏。

**安全说明**：localStorage 存令牌是桌面应用的常规做法（我们的 Electron 壳里页面都是自己的代码，没有第三方脚本注入面）。将来真要上生产，还有"令牌刷新"（快过期时悄悄换新票）可做，记在打包/部署章的账上。

**验收剧本（已通过）**：登录→/api/me 返回正确身份；无令牌401；伪造令牌401；普通用户 isAdmin=false；禁用账号后旧令牌立即401、恢复启用后又能用。

## 2026-10-01 · 第 15 章：挂单锁定（v0.15）—— 并发裁决从"确认"提前到"挂单"

**做了什么**：货品新增"锁定"状态，**无需迁移，纯逻辑改造**（item.status 本就是自由文本，这是当初没加 CHECK 约束歪打正着的好处，也是坏处——状态集合只活在代码里，将来权限/盘点章节要把状态机文档化）。生命周期全链路：挂单(保存草稿)即 在库→锁定；草稿换货=旧件解锁+新件上锁；删草稿全解锁；确认收款 锁定→已售；反确认 已售→**锁定**（不是在库！单据回到草稿、草稿仍占着这些件——想释放就删草稿或移出明细）。库存筛选加"锁定"选项，扫码提示会说"已被挂单锁定（在某张销售草稿里占着）"。

**关键决策**：
- **并发裁决提前**：v0.11 的裁决在"确认收款"——两个柜台可以同时把同一件货加进各自草稿，顾客A试戴半小时，柜台B先收了款，A这边确认时才报错，顾客体验稀碎。现在裁决在"挂单"那一刻（`UPDATE item SET status='锁定' WHERE status='在库'`，还是同一招条件更新），谁先挂谁得，后来者立刻知道。
- **解锁+上锁+存单一个事务**：编辑草稿时先把旧明细整体解锁、再按新明细逐件上锁，中途任何一件抢不到就整体回滚——不会出现"换货换一半"的中间态。
- **跨单据守卫零成本延伸**（第7章的老设计在还利息）：退库单确认查的是 status='在库'，锁定件自然被拒——"锁定件不能退库"这条规则一行代码都没写，是从状态机里自动长出来的。
- **stock_flow 只记库存事实**（在库/已售/已退库之间的变化，以及反确认的回退），挂单锁定/解锁这类预订性质的操作不记流水——否则改两次草稿就刷十几条流水，审计日志全是噪音。锁定的追溯靠货品状态+草稿本身。
- **兼容老草稿不特判**：v0.14 前的草稿里件还是"在库"。解锁语句 `WHERE status='锁定'` 对它们自然空转；确认接受 锁定/在库 两种来源状态（FOR UPDATE 锁行读状态，真实来源状态记进流水）。

**验收剧本（10项全过）**：挂单后件变锁定；第二张单抢挂被拒；锁定件退库被拒；草稿换货旧解新锁；删草稿全解锁；确认 锁定→已售；反确认 已售→锁定且别的单抢不走；再确认成功；流水链 在库→锁定→已售→锁定→已售 完整可查（锁定↔在库的挂单操作不在流水里，符合设计）。

**下一站**：v0.16 销退单——跨日退货的正规出口。

## 2026-10-01 · 第 16 章：分单据类型的占用状态（v0.16）—— 用户抓出的洞 + 用户提出的更好方案

**问题由来（用户实测发现）**：退库单反确认后，货品直接回"在库"——但单据退回了草稿，草稿还占着这些件，别的单能把货抢走。这正是第15章在销售单上刚修掉的毛病，我只改了销售单，退库单漏了。**教训：一个模式修正了，要横向检查所有同构的地方**——单据引擎里每种单据都有同样的生命周期，补丁也得全家桶。

**用户的方案（比我的更好）**："一个商品进入任何单据的草稿都该被占用，而且占用状态按单据类型命名——退库草稿='退库中'，销售草稿='销售中'。"比统一叫"锁定"多一层信息：库存列表里一眼看出货在哪类单里，店员不用翻单据猜。采纳，全盘重构。

**做了什么**：
- "锁定"更名"销售中"（代码+迁移011转换存量货品与历史流水）；
- 退库单补全同款生命周期：挂草稿 在库→退库中；草稿换货=旧解锁新上锁（一个事务）；删草稿解锁；确认 退库中→已退库（FOR UPDATE读真实来源状态记流水，兼容老草稿的在库）；**反确认 已退库→退库中**（本次的bug修复点）；
- 库存筛选项：销售中/退库中；扫码提示"被某张草稿占着——先处理那张草稿"。

**关键决策**：
- **占用状态=单据类型的投影**：将来盘点草稿、维修单同理扩展（盘点中/维修中）。状态命名约定定下来了：`xx中` = 被某张未确认单据占用，`已xx` = 单据确认后的事实状态。
- 迁移011**连历史流水一起改名**——审计链里新旧名字混用，三个月后没人记得"锁定"和"销售中"是同一回事。
- 交叉守卫继续零成本：退库中的件销售挂不进、再退也退不了、入库单反确认也会被挡——全部来自"条件更新 WHERE status='在库'"这一招，没有为任何一条规则单独写代码。

**验收剧本（11项全过）**：退库挂草稿→退库中；销售抢挂被拒；重复退库被拒；换货A解B锁；删草稿解锁；确认→已退库；反确认→退库中且销售抢不走；再确认成功；销售侧改名后全流程（销售中→已售→销售中→删草稿→在库）照常；存量"锁定"清零。

**下一站**：v0.17 销退单（跨日退货正规出口）。

## 2026-10-01 · 第 17 章：销退单（v0.17）—— 销售闭环收口

**做了什么**：销退单（XT）全生命周期，跨日退货的正规出口。扫码只收"已售"的件，`/api/sale-return/lookup` 自动带出原销售单号与原成交价（从原单金价快照里查）；退款默认原价、可下调（扣损耗）、**不得超过原成交价**；退款走组合退款方式（与收款共用 pay_method 字典和校验：方式启用、不重复、合计分毫不差）。件状态：已售 →(挂草稿)→ **退货中** →(确认退款)→ 在库；反确认 在库→退货中，限当日。无迁移。

**关键决策**：
- **原单信息在挂草稿时查定、存进草稿**（origDocNo/soldPrice 写入 draft_lines），确认时不再追溯——单据一旦成立，它引用的事实就冻结在单据里，和金价快照同一个哲学。
- **"退货中"沿用第16章的命名约定**（xx中=被未确认单据占用）。由此免费获得一批守卫：退货中的件，原销售单反不了确认（验收5）、销售/退库都挂不进。
- **销退反确认的对手是"再销售"**：退货确认后货回在库，可能立刻被再次卖掉——反确认用条件更新 `WHERE status='在库'` 抢件，抢不回就报"退回的货可能已被再次占用"（验收10），绝不让同一件货同时活在两条时间线上。
- **删销退草稿回"已售"不是"在库"**——退货没发生，世界回到"卖掉了"的事实。每种草稿的解锁目标是它锁定前的状态，不是统一回在库。
- 反确认限当日与销售单对齐：跨日想再退重开一张销退单即可（销退单本身没有数量限制问题）。

**验收剧本（13项全过）**：lookup带原单与原价；在库件拒收；退款超原价拒；挂草稿→退货中；原销售单反确认被挡；无退款方式拒；合计不符拒；组合退款(1400+1000)确认→在库；退回货再销售正常；被占用时销退反确认拒；释放后反确认成功；删草稿→已售。

**至此销售闭环齐了**：入库→(挂单锁定)→销售→当日反确认 / 跨日销退→再销售。下一步可选：售货员提成报表、分销商模块、盘点、列模板/筛选器、打印。

## 2026-10-01 · 第 18 章：分销商模块——位置维度与统一调拨单（v0.18）

**业务口径（与用户确认）**：本期只做库存流转（门店销售待"账号绑门店"后放开）；分货暂不记价；流转路径支持 总库↔分销商 以及**分销商互调**（本代理商名下）。

**做了什么**：分销商档案维护（增/改名/停用，按id引用改名安全）；货品"位置"维度上线（001迁移早埋好的 location_type+distributor_id，这次真正用起来）；**统一调拨单（DB）**：一种单据三种用法——总库→分销商＝分货、分销商→总库＝退回、分销商A→B＝互调。全生命周期：挂草稿 在库→**调拨中**；确认 位置变更+回在库；反确认 从调入方拉回（条件更新，已被占用则拒）；删草稿解锁留在调出方。库存查询加位置列+位置筛选，汇总同口径。迁移012只给 doc 加 from/to 两列。

**关键决策**：
- **位置与状态是正交的两个维度**：状态答"这件货处于什么业务阶段"（在库/已售/xx中），位置答"它在谁手里"（总库/某分销商）。在库的货可能在任何位置；调拨改位置不改状态本质。想明白这一点，整个模块就是"锁定→改位置→解锁"。
- **一种单据吃掉三种业务**是"分销商可互调"决定的：若做成分货单+退货单两种，互调还得加第三种；统一成 from→to 后三种只是参数不同，代码只写一遍，对账只查一张表。NULL=总库（外键列不能存0）。
- **销售/退供应商挂上位置守卫**（AND location_type='总库'）：分出去的货在总部开不了单，错误提示直接告诉店员货在哪、该怎么办（"在「东门店」处，请先调拨回总库"）。这是本章唯一动到旧单据代码的地方。
- **互调不经总库直达**，但反确认同样用条件更新拉回——货在西门店已被再次占用就拒绝，继续"同一件货不活在两条时间线"。
- 调拨单反确认不限当日：它不是财务单据，是库存位置纠错，随时可反（当然要抢得回货）。

**验收剧本（15项全过）**：建档；from=to拒；分货挂草稿→调拨中；占用期销售拒；确认→在库@东门店；门店货销售/退供应商/被总库再调全拒（提示带位置）；互调成功；互调反确认拉回；删草稿留在原地；退回总库后恢复可售；停用分销商不能当端点；位置筛选准确；流水带 from_loc→to_loc 全程可溯。

**下一步候选**：账号绑门店+门店销售、售货员提成报表、盘点、列模板/筛选器、打印spike。

## 2026-10-01 · 第 19 章：账号绑门店+门店销售（v0.19）

**登录方案的讨论（值得记）**：用户原方案是两段式——先输代理商密码进入代理商空间，再登个人账号。方向对（先定位数据空间、再定位人），但第一层共享密码是隐患：**所有店员都知道的密码约等于没有密码**（离职带走、轮换困难）。定稿方案：门店在**建账号时绑死在账号上**（app_user.distributor_id，NULL=总部），登录一步到位；服务端每个请求实时从账号推导"你是谁、哪个店、能卖哪里的货"——客户端一个字不传，伪造无门，改绑/禁用立即生效。"代理商代码"这层留到将来上云多代理商时再加（它只是门牌号不是秘密；且推荐每个代理商独立数据库）。

**做了什么**（迁移013只加一列）：
- 建账号可选所属（总部/某门店），用户列表显示所属；登录和 /api/me 返回门店，界面头部显示"当前用户：小张（东门店）"。
- **门店账号的世界自动缩小到本店**：库存强制只看本店（无视客户端传的位置参数）；销售/销退只能动本店位置的货（锁定条件直接带位置）；销售单/销退单列表只见本店，确认/反确认/删除他店单据403。销售单和销退单落库时带 distributor_id——单据从此有了"属于哪个店"。
- **入库/退库/调拨/字典/金价发布是总部职能**：门店账号写操作403，列表返回空；前端对应卡片按身份隐藏（老规矩：前端隐藏是体验，服务端403是安全）。
- 对称性：总部账号同样不能卖门店的货、不能替门店办销退（lookup直接提示"是「东门店」卖出的件，请在该处办理"）。

**验收剧本（12项全过）**：建门店账号；登录带门店；库存强制本店视角；卖总库货被拒；卖本店货成功；总部卖门店货对称被拒；门店动入库/调拨/退库全403；单据列表按店隔离；跨店反确认403；门店销退本店件闭环（退完在库@东门店）；总部销退门店件被引导去门店；用户列表带所属。

## 2026-10-01 · 第 20 章：提成模块（v0.20）—— 规则管理 + 多售货员分成 + 确认入账

**口径（与用户确认后定稿）**：规则按 **大类×结算方式** 配置，每条三选一算法（销售额百分比 / 每克固定 / 每件固定）；一张单 1~3 个售货员**整单平分**；**店长从本店店员的提成里抽成**（店员到手=份额×(1-抽成%)，店长自己卖货按规则全额拿）；销退自动按原单冲减。

**做了什么**（迁移014）：
- `commission_rule` 规则表（大类×结算方式唯一）+ 管理界面（管理员"提成规则"按钮）；
- 售货员档案补齐 **门店归属/角色(店员/店长)/店长抽成%**，并强制"**一店一店长**"（创建/改角色/重新启用三个入口都校验——否则抽成归属不清）；
- 销售单改**多售货员**（salesperson_ids JSONB，点名字选中，最多3人；存量单据自动回填）；确认时校验每位售货员在职且**归属与单据门店一致**（门店的人不能上总部的单记提成）；
- `commission_flow` 提成台账（只追加）：确认收款那一刻按规则算出每件货的提成→平分→店员份额被店长抽成，逐行入账；**当日反确认=删除该单台账**（单据重开）；**销退确认=按原单逐件写负数冲减行**（店长抽成同步冲）；销退反确认再删冲减。

**关键决策**：
- **提成是确认时刻的快照**：改规则、改抽成比例、售货员调店，都只影响之后确认的单——已入账的不回算。和金价快照同一哲学：单据一旦成立，它引用的事实冻结在单据里。
- **没配规则=没提成，不报错**：新大类先卖着，规则补上后新单生效。拦住开单是把提成配置变成了销售的前置条件，本末倒置。
- **台账只追加（冲减用负行）**，报表=对台账做 SUM——下一章的提成报表不需要任何新的计算逻辑，只是查询。
- 平分用 round2(总额/人数)：分不尽的厘头差异可忽略（提成口径本就按分截断）。

**验收剧本（12项全过）**：规则建立/重复维度拒；一店一店长拒；两店员平分+店长抽成（300→各135+老李30）；店长自卖全额（每克3元×10g=30）；门店售货员上总部单被拒；反确认台账清空；销退冲减-30、老李净额归零；无规则大类正常卖且0台账；列表多人"小红、小王"；4人拒。另外沙盒里停用状态的小红把两个用例拦下——"停用售货员不能确认"顺带得到了真实验证。

**下一站**：v0.21 提成报表（按期间×人汇总台账，含店长抽成与冲减分列）。

## 2026-10-02 · 第 21 章：提成报表（v0.21）+ 踩坑10：负数四舍五入

**做了什么**：管理员新增"提成报表"：选起止日期（默认本月），按售货员分列 成交单数/销售提成/店长抽成/销退冲减/净提成，底部合计行。**无迁移、后端只加一个查询接口**——因为第20章把台账设计成只追加的流水，报表=一句带 `FILTER (WHERE kind=...)` 的 GROUP BY，没有任何新计算逻辑。这就是"写时多记一点，读时不用算"的回报。

**踩坑10（报表第一次跑就抓到的真bug）**：合计里销退冲减显示 **-29.99** 而不是 -30。原因：`round2` 旧实现 `int64(v*100+0.5)`——对正数是四舍五入，对负数却是"加0.5再向零截断"：-30×100+0.5=-2999.5，int64截断成-2999，于是-29.99。这个函数从第11章用到现在一直正确，因为**此前它只见过正数**；第一次对负数合计取整就露馅。修复：`math.Round(v*100)/100`，正负都正确。教训：**测试数据要覆盖负数、零、边界**，"一直没出错"不等于"对"。

**验收**：三人报表（小红135/小王135/老李 销售30+抽成30-冲减30=净30），合计净300；缺日期400；非管理员403；修复后 totalReturn 精确-30。
