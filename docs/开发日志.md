## 2026-10-01 · 第 0 章：环境搭建

**做了什么**：Homebrew → Git/Go/fnm(Node)/OrbStack(Docker)/VS Code → GitHub SSH 推送 → PostgreSQL 容器。

**关键决策**：
- 工具只从 Homebrew 装；版本声明进项目文件（go.mod/.nvmrc）；数据库跑 Docker 容器不装进系统——"干净"的定义是**可重建**，不是电脑里没东西。
- 代码放 `~/dev/`（避开 iCloud 同步、路径无空格无中文、不会被当下载垃圾清理）。
- 仓库设为 Private；`.gitignore` 必须在第一次 `git add` 之前写好（node_modules 几万个文件进仓库是新手经典事故）。

**踩坑记录**：
1. *Command Line Tools 安装失败（invalid developer directory）*——机器上有完整版 Xcode，独立 CLT 根本不用装，`sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer` 把指针指回 Xcode 即可。教训：报错先读字面意思，"目录无效"就是指针指错了。
2. *装完 OrbStack 后 `docker: command not found`*——OrbStack 要**首次打开 App** 才会创建 docker 命令；而且 PATH 变更只在**新开的终端标签**生效。教训：装完 GUI 工具先打开一次；环境变量问题先开新终端再排查。
3. *brew 提示 VS Code already exists*——已装过的软件 brew 拒绝覆盖，无害，跳过即可。

## 2026-10-01 · 第 1 章：跑通骨架（v0.1，内存版）

**做了什么**：Go 标准库后端（零依赖）+ Vue3 前端，登录/入库/库存三个功能，数据存内存。

**为什么这么做**：先让"浏览器→API→业务逻辑"整条链路亮起来，再谈数据库。零依赖意味着 `go run main.go` 必跑通，第一次体验不会被网络/代理问题劝退。

**这版埋的三个真概念**（后面所有版本都围绕它们展开）：
- 单号服务端发号：`RK + YYYYMMDD + 2位序号`，日上限 99；
- 条码双模式：留空自动生成 / 填写则校验（仅 A-Z0-9 + 全局唯一）；
- **全有或全无**：任何一行校验失败，整单不入库。

## 2026-10-01 · 第 2 章：接入 PostgreSQL（v0.2）

**做了什么**：`database/sql + lib/pq` 连接 Docker 里的 PG16；入库改为一个数据库事务；发号器落到 `doc_counter` 表；每件货写 `stock_flow` 库存流水。

**关键决策**：
- 驱动选 `lib/pq`（零依赖、database/sql 标准接口）而不是 pgx——对入门更友好，将来要换也只是换 import。
- "全有或全无"从"代码小心点"升级为**数据库事务保证**：`db.Begin()` → 全部成功 `Commit()` / 任何失败 `defer Rollback()`。
- 发号器 SQL：`INSERT ... ON CONFLICT ... DO UPDATE SET seq=seq+1 RETURNING seq`——一条语句完成取号，天然并发安全（先在 psql 里手跑两次看到 1、2，再写进代码）。
- 金额克重全用 NUMERIC；表名用 app_user（user 是 PG 保留字）；条码规则在数据库层再加 CHECK 约束兜底。

**验收仪式**：开两张单 → 重启后端 → 数据还在。`stock_flow` 里能看到每件货的"(入库)→在库"记录。

**踩坑记录**：
4. *psql 里粘贴多行 SQL 后界面卡死、报 sh 语法错误*——`\d` 的长输出进了翻页器(less)，粘贴的内容被当成按键命令。按 `q` 退出；`\pset pager off` 关掉翻页；**长 SQL 压成一行再粘贴**。
5. *`go mod tidy` 毫无输出*——因为 main.go 还是旧版、没有新依赖，它无事可做。教训：命令"没反应"时先确认前置步骤真的生效（`head -3 main.go` 看文件版本）。

## 2026-10-01 · 第 3 章：单据状态机（v0.3）

**做了什么**：入库从"一步到位"拆成 **保存草稿 → 确认 → 反确认 / 删除草稿**。草稿明细存 `doc.draft_lines`(JSONB)，确认那一刻才生成货品件；前端加单据列表、状态徽章和操作按钮。

**关键决策**：
- **确认 = 业务生效点**：库存只在确认时变动，和单据状态变更在同一事务里（设计文档 4.2 节的落地）。
- **条件更新裁决并发**：`UPDATE doc SET status='已确认' WHERE id=$1 AND status='草稿'`——两台电脑同时点确认，数据库保证只有一台影响行数=1，另一台得到人话报错。整个系统的并发安全就建立在这一个模式上。
- **反确认的下游校验**：本单所有件必须仍"在库"，否则拒绝并指明条码（现在只有入库单，将来销售/分销单引用了件，这道闸自然生效）。
- **条码不重发**：确认时把发出的条码回写进草稿明细；反确认→再确认，条码原样复用。吊牌已经打了，条码换了就全乱了——业务常识决定技术设计。
- 草稿即占号，删除不回收（号段留空洞没问题，号被复用才是审计灾难）。

**踩坑记录**：
6. *点反确认后整个页面按钮全部失灵*——**本项目第一个真实 bug**，值得详记：
   - 现象：反确认成功，但之后点任何按钮都没反应。
   - 本质：一张单据的 items 字段返回了 null，模板里 `d.items.length` 抛 TypeError，**Vue 渲染函数一旦抛异常，整个组件树冻结**，表现为"所有按钮失灵"。
   - 排查法：界面全体失灵 ≈ 渲染异常 → 开浏览器开发者工具(Cmd+Option+I)看 Console 红字，一眼定位到行。
   - 修复（两层）：后端——反确认时从真实货品件**重建**草稿明细，且列表接口永远返回数组不返回 null（API 卫生）；前端——`d.items?.length ?? 0`、`(it.weightG ?? 0).toFixed(2)` 渲染防护。
   - 教训：后端给的数据永远可能有缺口，前端渲染永远要防 null；临时恢复手段是刷新页面，根治靠两端兜底。
7. 开发期数据可以随时清零重来：`TRUNCATE ... RESTART IDENTITY` 只清数据不动表结构。但**健壮性修复不等于兼容补丁**，该留的防护要留下。

## 附：如何用 git 倒推学习

每条提交都是整个项目在那一刻的**完整快照**，所以答案是：可以，而且不用"下载"，仓库里全都有。

常用回放命令：

```bash
git log --oneline            # 列出全部提交（哈希+说明），就是本日志的目录
git show <哈希> --stat       # 看某次提交改了哪些文件
git show <哈希>              # 看该次提交的完整代码差异（+是新增，-是删除）
git diff <旧哈希> <新哈希>   # 对比任意两个版本
git checkout <哈希>          # 把整个工作区切回那个时刻（时光机）
git checkout main            # 回到最新（看完记得回来！）
```

两个习惯让回放更有价值：**一次提交只做一件事**，提交说明写清楚"做了什么"（本仓库一直如此）；GitHub 网页上的 Commits 页签也能点开每次提交在线看差异，适合不想碰命令行的时候。

学习路线建议：`git log --oneline` 从最早的提交开始，对照本日志的章节，`git show` 逐个看差异——你会看到系统像搭积木一样从 200 行长到现在，每一步的"为什么"都在上面的章节里。

## 2026-10-01 · 第 4 章：真实账号体系（v0.4）

**做了什么**：登录改为查 `app_user` 表；密码用 PBKDF2-HMAC-SHA256 加盐哈希存储（Go 标准库 crypto/pbkdf2）；登录成功签发 JWT(HS256, 12小时过期)；鉴权中间件验证令牌并把用户id放进请求上下文；单据制单人、库存流水操作人全部换成真实 uid；新增修改密码接口和界面；首次启动若无用户自动创建 admin/123456 并提示改密。

**关键决策**：
- **数据库永远只存哈希不存明文**：`pbkdf2:迭代次数:盐:哈希` 一串存下自描述参数，将来升级迭代次数也能平滑过渡；校验用恒定时间比较防时序侧信道。
- **JWT 无状态认证**：服务端不存会话，令牌自带身份和过期时间，天然适配多终端同时登录；密钥走环境变量 `JWT_SECRET`（上线前必须换掉默认值）。
- 登录失败只回一句"账号或密码错误"——不泄露"账号是否存在"。
- 改密码必须先验旧密码；新密码至少6位（权限框架做好后可加策略）。

**踩坑记录**：
8. *首次启动 panic: value too long for type character varying(100)*——哈希串112字符超过 password 列宽。测试环境先于用户炸出，加迁移 003 放宽到 VARCHAR(200)。教训：**改了数据的"形状"（更长/更多/类型变了），先想想列宽和约束**；也再次验证"先在测试环境全链路跑一遍再交付"的流程价值。
